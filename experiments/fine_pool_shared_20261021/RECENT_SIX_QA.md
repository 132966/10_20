# 最近六次技术问答：共享缓存、精筛接口与原生池

按最近六个相关技术问题整理，省略中间的执行指令。回答保留核心意思，并明确之前容易混淆的地方；这是整理版，不是逐字聊天记录。

最终采用的方向：**原生池仅作为准备阶段的复制源；把公共候选复制一次到精筛池，原DeepGEMM仍只读一个精筛池。没有实现精筛直接读取原生池。**

## 1. “既然已经允许修改精筛的寻址方式，这是啥意思？”

答：寻址方式就是根据候选编号，计算K在显存中的地址。

旧逐Q缓存里，第i个候选已排好，直接读本Q区域。独立共享实验中，先把i还原成原序列逻辑位置，再找到公共缓存的页及页内位置。

这里“已经允许”措辞不准确：当时只是独立实验写了一个配套consumer，**没有修改原项目的正式精筛算子**。

本次进一步兼容原DeepGEMM：数据仍放在单一fine池中，各Q通过自己的页表引用共享页，DeepGEMM的打分kernel不用改。

## 2. “Q0为啥需要独立缓存？”

答：Q0并不必须有独立的HBM K副本。它只需要自己的候选范围，以及找到相应K的办法。

原实现用 `CAP + row * SCRATCH + p` 给各Q预留区域，是当时的数据组织方式，不是数学计算或CUDA Graph的强制要求。

```text
每Q有自己的页表：需要
每Q有一份重复的K数据：不必
```

打分时把数据读入寄存器/片上执行资源，不等同于先给每Q复制一份HBM缓存。

## 3. “不懂啦，要符合之前精筛的实现和cuda graph那些输入要求，你觉得现在这个怎么实现比较好？”

答：保持原DeepGEMM的单池输入，把公共数据放进同一个 `fine` 池：

```text
fine池：[历史重排页][共享sink＋tail页]

每Q页表：[选中的历史页][共享sink页][该Q需要的共享tail页]
```

各Q页表可以引用相同物理页。CUDA Graph提前固定缓冲区地址和容量，回放时更新页表、长度、预算和实际发布终点。

非页对齐的tail会导致边界页带入额外位置，因此需要正确过滤和输出映射。不能只替换复制kernel就假定其余流程自动兼容。

本次实现的方式是：原DeepGEMM打分后，用一个kernel同时进行边界过滤和候选分数顺序恢复，TopK继续看到旧式的连续候选顺序。

## 4. “没太理解，能不能简单说清楚？”

答：把A/B/C/D看成数据页。

```text
原来：
Q0复制 [A B C]
Q1复制 [B C D]

现在：
fine池只保存 [A B C D]
Q0页表引用 A B C
Q1页表引用 B C D
```

B和C只存一份，两张页表都可以指向它们。精筛照旧按页表读数据、打分；无效边界位置在TopK前排除。

## 5. “为啥不是不同Q0直接指向一份最原始的那个，而是要把原始的复制成一份公共的，指向公共的呢？”

答：不是直接读取原生数据不正确，而是原DeepGEMM本次调用只接收一个K池基地址。

```text
历史选中页位于重排/精筛池fine
sink和未建索引尾部位于原生池native
```

如果把原生页20直接填入原精筛页表，算子会读 `fine[20]`，不会自动切换成 `native[20]`。

复制一次是为了让两类候选位于同一个fine池，保留现有接口。CUDA Graph本身并没有要求必须复制。

## 6. “稍等，直接读取原生池会有啥问题吗？”

答：直接读原生池在正确性和CUDA Graph上没有天然障碍，但需要处理：

1. 两个池的寻址：要修改精筛支持双池，或者拆成两次单池打分后合并。
2. 每Q不同的窗口、因果边界、候选去重与逻辑位置映射。
3. 原生K写入完成、页不被回收或覆盖、跨流事件顺序。
4. 性能：省掉复制，可能增加寻址、打分启动和结果合并成本，必须实测。

用户最终选择不走这条改动更大的路线。**本次代码没有让DeepGEMM读取原生池；只在准备阶段从原生池搬运一次，之后仍然从fine池打分。**

## 与本次代码的对应

- `tail_union.py`：公共候选页复制到fine池的预留区域。
- `kernels.py::tables`：为每个Q生成指向同一fine池的页表和长度。
- `experiment.py::Runner.fine_score`：直接调用未修改的DeepGEMM分页精筛。
- `kernels.py::normalize`：过滤边界/因果/重叠成员，同时恢复连续候选顺序。
- `kernels.py::map_topk`：把选中的候选编号映射回逻辑位置和原生slot。

当前是独立实验，已经具备真实DeepGEMM接口验证；不是已经修改并部署到了原SGLang模型运行路径。TopK验证采用两边相同的PyTorch预分配TopK，并非声称生产版融合TopK已经接入。
